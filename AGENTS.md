# AGENTS.md

## Project state

Drogon plugin library for the OneBot v11 protocol, consumed by other Drogon apps (e.g. `../assistantbot`). It implements the HTTP API (calling actions) and HTTP POST reporting (receiving events), tested against NapCat's behavior. WebSocket transports are not implemented.

- The library target is `drogon-onebot` (alias `drogon-onebot::drogon-onebot`). It is static by default; pass `-DBUILD_SHARED_LIBS=ON` for a shared build.
- Public headers live in `include/drogon_onebot/` and are installed through the `HEADERS` file set. Consumers include `<drogon_onebot/...>`. Private headers go in `src/`, which is only on the library's own include path.
- The plugin class is `drogon_onebot::OneBotClient` (`drogon::Plugin<OneBotClient>`). Apps register it by class name under `plugins` in their config.json. Drogon calls `initAndStart(config)` inside `app().run()`, before beginning advices, so `app().getPlugin<drogon_onebot::OneBotClient>()` only works after `run()` starts.
- Registration relies on drogon's static `DrObject<T>::alloc_` initializer. With the static library, the linker only pulls in `onebot_client.o` when the app references the class. If the app lists the plugin in config.json but never calls `getPlugin<OneBotClient>()` (or otherwise uses the class), drogon logs `Plugin drogon_onebot::OneBotClient undefined!` and keeps running without it.
- Plugin config keys:
  - `base_url` (the OneBot implementation's HTTP API, e.g. `http://127.0.0.1:3000`) is required.
  - `event_path` (e.g. `/onebot/event`) is optional and must start with `/`; without it no event route is registered.
  - `access_token_env` and `secret_env` are optional, and each names an environment variable. Secrets are never read from config.json. The first holds the HTTP API access token (sent as `Authorization: Bearer`); the second holds the secret that signs posted events.

  `initAndStart` throws `std::invalid_argument` if `base_url` is empty, if `event_path` is invalid, or if a named variable is unset or empty. Add new keys to `OneBotConfig`, `initAndStart`, the class doc comment, `config.json`, and the tables in `docs/*/drogon-plugin.md`.
- `OneBotClient::NewOneBotClient()` returns a `OneBot` by value. `OneBot` is a value handle whose only state is one `std::shared_ptr<details::Transport>`, so copies are cheap and go into coroutines by value. Its methods are coroutines returning `drogon::Task<Result<T>>` (`std::expected<T, Error>`, in `error.hpp`); there is no sync API.
- `OneBot` methods mirror OneBot v11 action names (`SendPrivateMsg` calls `send_private_msg`), as the common OneBot SDKs (NoneBot2, aiocqhttp) do, so there are no API group members. Request and response structs live in `types/`, one header per category; the method bodies live in `src/actions/<category>.cpp`. `CallAction(CallActionParams)` reaches any action, including implementation extensions, and yields the envelope's raw `data`.
- The typed actions (`GetLoginInfo`, `GetStrangerInfo`, `SendLike`, `GetFriendList`, `SendPrivateMsg`, `SendGroupMsg`, `SendMsg`, `DeleteMsg`, `GetMsg`, `GetForwardMsg`, `GetGroupInfo`, `GetGroupList`, `GetGroupMemberInfo`, `GetGroupMemberList`, `GetGroupHonorInfo`, `SetGroupKick`, `SetGroupBan`, `SetGroupWholeBan`, `SetGroupAdmin`, `SetGroupCard`, `SetGroupName`, `SetGroupLeave`, `SetGroupSpecialTitle`, `SetFriendAddRequest`, `SetGroupAddRequest`, `GetCookies`, `GetCsrfToken`, `GetCredentials`, `GetRecord`, `GetImage`, `CanSendImage`, `CanSendRecord`, `GetStatus`, `GetVersionInfo`, `SetRestart`, `CleanCache`) call `details::Transport::Call` and read their result from `data` with `details::FieldReader` (`src/details/field_reader.hpp`), the same reader that event parsing uses.
  - A missing or null member reads as absent; a member of the wrong type is a problem. The IDs and the main name or content fields are required; the other fields default to empty, 0, or false.
  - Any problem, including the null `data` of an `async` reply, becomes `ResponseValidation` through `details::invalid_data_error`, with `data` as the error body.
  - Integers are read with `details::read_integer<T>`, which accepts JSON numbers and decimal strings, because NapCat sends some IDs as strings.
  - Arrays (the list actions' `data`, `get_forward_msg`'s `messages`) are read with `details::read_array<T>`, which applies a per-entry reader (`to_friend_info`, `to_message_info`, ...) and names the failing entry, e.g. `data[1].nickname is missing`.
  - `StrangerInfo`, `MessageInfo`, `GroupInfo`, `GroupMemberInfo`, `FriendInfo`, `Cookies`, `FileInfo`, `Status`, and `VersionInfo` also keep the whole `data`, or list entry, in `raw`, because NapCat adds extension fields, and the standard lets implementations add their own to `get_status` and `get_version_info`.

### Transport

`details::Transport::Call(action, params, timeout)` implements the OneBot v11 HTTP API (`communication/http.md` and `authorization.md` in the botuniverse/onebot-11 spec):

- It sends `POST <base_url>/<action>` with the parameters as a JSON body, plus `Authorization: Bearer <access_token>` when the token is non-empty. A path in `base_url` becomes a prefix.
- It creates a new `HttpClient` for each request on the calling thread's loop, or on the main loop when the thread runs no loop, and keeps it in the coroutine frame until the response arrives. Don't cache one client for reuse: drogon's `HttpClient` defaults to pipelining depth 0, so a shared client would serialize concurrent requests.
- Failure mapping:
  - A `drogon::HttpException` with `ReqResult::Timeout` is `Timeout`; other codes are `Connection`.
  - A non-2xx status (the spec uses 400, 401, 403, 404, and 406; NapCat answers a bad token with 403) is `Status`.
  - A 2xx body that is not JSON, or has no `status` string, is `ResponseValidation`.
  - The spec answers every other case with HTTP 200, so a failed action arrives as `"status": "failed"` and maps to `Action` with the envelope's `retcode` and its `message` (or `wording`) text. NapCat reports an unknown action this way too, with `retcode` 200.
  - `ok` and `async` both succeed and yield `data`, which is null for `async`.

### Events

`OneBotClient::initAndStart` creates a `details::EventReceiver` (`src/details/event_receiver.*`). When `event_path` is set, it registers a `POST` route there whose lambda shares that receiver.

- Registering a route from `initAndStart` works because drogon initializes plugins before routers (`HttpAppFrameworkImpl.cc:663-671`; `registerHttpController` asserts `!routersInit_`). Drogon's own `PromExporter` does the same (`PromExporter.cc:18`).
- The wire format follows NapCat's HTTP client (`packages/napcat-onebot/network/http-client.ts`): a JSON body, `x-self-id`, and, when its `token` is set, `x-signature: sha1=<hex HMAC-SHA1 of the body keyed by the token>`.
  - `EventReceiver` implements HMAC-SHA1 on `trantor::utils::sha1`, so the library needs no direct OpenSSL dependency.
  - It compares the hex digits case-insensitively and in constant time.
- The route answers before any handler runs:
  - 401 when a secret is set and `X-Signature` is missing; 403 when it does not match.
  - 400 with a text reason when the body is not a JSON object, a required field is missing, an integer field is not an integer, or `message` is not a segment array (NapCat's `messagePostFormat: string`).
  - 204 otherwise. NapCat keeps its request open until the response, and handlers may await for seconds (an LLM call), so the response never waits for them. This rules out quick operations (a `reply` in the response body).
  - Unknown `post_type` values, such as NapCat's `message_sent`, get 204 and are dropped.
- Dispatch is by `post_type`: `OnMessage`, `OnNotice`, `OnRequest`, and `OnMetaEvent` (aiocqhttp's names) append to per-type handler lists.
  - `MessageEvent` has typed fields. `NoticeEvent::detail` is `NoticeDetail`, a `std::variant` of one struct per notice type, which `read_notice_detail` fills by `notice_type` through a `to_<type>_notice` reader. Its required fields are plain members, and a missing or mistyped one is a 400, as for messages. Any other notice, NapCat's extensions included, gets `std::monostate`. The request and meta events have only `time`, `self_id`, their type, `sub_type`, and the whole event in `raw`.
  - `group_upload` (`napcat-onebot/api/group.ts:292-306`) sends the file's `id` as a `FileNapCatOneBotUUID` string, `size` parsed from QQ's string, and QQ's `fileBizId` or 0 as `busid`. `to_group_upload_notice` requires `file.id` and `file.name`.
  - `group_admin` comes from QQ's system message of type 44, with `sub_type` `set` or `unset`, after NapCat refreshes its member cache (`napcat-onebot/api/msg.ts:1509-1525`).
  - `group_decrease` comes from QQ's system message of type 34 (`napcat-onebot/api/msg.ts:1455-1508`). NapCat maps QQ's decrease type to `sub_type` `leave`, `kick`, `kick_me`, or its own `disband`, and anything else to `kick` (`:1398-1411`). Here and in `group_increase`, `operator_id` comes from QQ's push or, when the bot is an admin or the owner, from a group notification within a second (`:1412-1433`), and is 0 otherwise.
  - `group_increase` comes from QQ's system message of type 33, with `sub_type` `invite` for QQ's type 131 and `approve` otherwise (`napcat-onebot/api/msg.ts:1440-1454`), and from gray tips: the bot's own join as `approve` with `user_id` the bot account, an invitation of the bot as `invite`, and a "joined the group" tip as `invite` with `operator_id` 0 (`napcat-onebot/api/group.ts:320-369`).
  - NapCat never sends `MessageEvent`'s `anonymous`, or `sub_type` `anonymous`, because QQ NT has no anonymous chat. Its `sender` holds only `user_id`, `nickname`, `card`, and, in groups, `role` (`napcat-onebot/api/msg.ts:1139-1173`), in events, `get_msg`, and `get_forward_msg` alike. It emits no `notify` notice with `sub_type` `lucky_king` or `honor`; no source under `napcat-onebot/` names them. They get no typed member, by decision; `raw` keeps whatever another implementation sends.
  - Each handler gets its own `drogon::async_run` task. The task's lambda copies the handler and the event, and `async_run` moves that lambda into its coroutine frame (`coroutine.h:749-762`), so a handler's captures outlive the request.
  - The task catches and logs exceptions, because an exception escaping an `AsyncTask` calls `std::terminate` (`coroutine.h:397-401`).
- Handlers must be registered before the listeners start: in a beginning advice, or in `initAndStart` of a plugin that lists this one under `dependencies`. The lists are read from IO threads without a lock. `On*` logs a warning when `event_path` is not set.
- `On*` must not be called before `initAndStart` has run, because `m_receiver` is created there. That is always true once `getPlugin` works.

## Consuming the library

Keep both ways working when you change `CMakeLists.txt`.

- From source: `add_subdirectory(<path>)`, or CPM with `SOURCE_DIR`/`GIT_REPOSITORY`. `PROJECT_IS_TOP_LEVEL` is false then, so `DROGON_ONEBOT_BUILD_TESTS` and `DROGON_ONEBOT_INSTALL` default to OFF, and neither the tests nor `enable_testing()` reach the consumer. `../assistantbot` with `-DCPM_drogon-onebot_SOURCE=<this checkout>` builds the library with its `-std=gnu++26`.
- Installed: `just publish` installs into `publish/`. Consumers set `CMAKE_PREFIX_PATH` to that directory and call `find_package(drogon-onebot CONFIG REQUIRED)`. The package config calls `find_dependency(Drogon CONFIG)`, so consumers don't need their own `find_package(Drogon)`. Version compatibility is `SameMinorVersion`.
  - The GitHub Release packages (`drogon-onebot-<version>-<os>-x64`, see the Release workflow below) are the same install tree plus `LICENSE`, from the release build only. Consumers still get drogon from vcpkg, with `x64-windows-static-md` on Windows.
- Either way, link `drogon-onebot::drogon-onebot`. It carries `Drogon::Drogon` publicly.

## Tests

The tests use drogon's own framework, `drogon/drogon_test.h`, which is installed with drogon, so the tests add no dependency.

- `tests/CMakeLists.txt` globs `tests/test_*.cpp` (non-recursive, `CONFIGURE_DEPENDS`) and builds each file into its own executable named after the file stem (`build/<preset>/tests/test_events`). Adding a `tests/test_*.cpp` file is enough. Removing one leaves its old binary until `just clean`.
- Each executable is registered with CTest: `WORKING_DIRECTORY` is the repo root (for `config.json`), `TIMEOUT` is 60, and `RESOURCE_LOCK config_json_listener` serializes them under `ctest -j`, because the app-backed tests share the listener port.
- The executables take drogon's test options: `-r <name>` runs one `DROGON_TEST`, `-s` prints passing checks, and `-l` lists the tests.
- `tests/support.hpp` holds the shared helpers:
  - `run_tests_with_app` follows drogon's `lib/tests/main_CookieSameSite.cc`. It runs `app().run()` on a background thread and waits for a beginning advice plus `LISTEN_DELAY`, because listeners start after the advices. Then it runs the tests on the main thread and quits the app.
  - The test thread runs no event loop, so tests may block on `drogon::sync_wait` (actions) or `HttpClient::sendRequest` (`post_event`).
  - `sendRequestCoro` returns an awaiter, not an awaitable, so `sync_wait` rejects it.
  - `Inbox<T>` passes events from handlers on IO threads to the test thread.
- `config.json` (tracked, no secrets) is the shared fixture. It listens on `127.0.0.1:18080`, which `base_url` points at, and sets `event_path` `/onebot/event` and `secret_env` `DROGON_ONEBOT_TEST_SECRET`. The tests set that variable themselves.

| Test | What it covers |
| --- | --- |
| `test_config` | Calls `initAndStart` on test-built plugins without running the app: required keys, both `_env` keys, `event_path` validation, and the tracked `config.json`. |
| `test_actions` | Serves a fake NapCat HTTP API. Covers `CallAction`'s body, `Authorization`, and path prefix; `async`; every `ErrorKind`; and the typed actions, with `data` shaped like NapCat's source, including missing and mistyped `data` fields, passed-through `Action` errors, and `no_cache` and the `send_msg` targets sent only when set. The info fakes echo the request body as `request` in `data`, which tests read back through `raw`. The setter fakes (`serve_setter`) record each request body in an `Inbox`, which tests take back with `sent_to`, and serve a `/failing/` variant. The 404 and non-JSON cases log drogon JSON `Syntax error` lines; that is expected. |
| `test_events` | Exercises the signed event route. RFC 2202 vectors check the test's own HMAC, and one NapCat body carries a signature computed independently with Python. Also covers uppercase signatures, string IDs, the 401/403/400 rejections with no handler run, all four event types, typed notice details and a notice missing a typed field, `message_sent` being dropped, several handlers per event, a throwing handler, and the response not waiting for a slow handler. |
| `test_events_unsigned` | Loads `config.json` without `secret_env` (`app().loadConfigJson`) and checks that unsigned events are accepted and any `X-Signature` is ignored. |
| `test_segments` | Runs without the app. Checks every `MessageSegment` constructor, including IDs sent as strings, and a message that mixes built and hand-written segments. |

- `CallActionUnreachableIsConnectionError` (`test_actions`) connects to `127.0.0.1:1` with a 10 s timeout. Windows retries a refused connect for about 2 s before it reports the failure, so a timeout of 2 s or less yields `Timeout` there instead of `Connection`. On Linux the connect fails immediately.

## Commands

`just` drives the build. Recipes map onto CMake presets named `<os>-<profile>` (`linux-debug`, `linux-release`, `windows-debug`, `windows-release`), with build trees in `build/<preset>/`.

- `just init`: run `vcpkg install` for the packages in `vcpkg_deps` (currently `drogon`), in classic mode (no `vcpkg.json`; `VCPKG_ROOT` must be set). On Windows it passes `--triplet x64-windows-static-md --host-triplet x64-windows-static-md`, so the dependencies are static libraries linked against the dynamic CRT, and the `windows-base` preset sets `VCPKG_TARGET_TRIPLET` to the same triplet so `find_package` looks in that installed tree. Keep the two in sync: the vcpkg toolchain ignores `VCPKG_DEFAULT_TRIPLET` and would fall back to `x64-windows`. Other platforms use vcpkg's default triplet.
- `just build [debug|release]`: configure only if `build/<preset>/CMakeCache.txt` is missing, then build, then copy `compile_commands.json` to `build/`. After a failed configure, run `just configure debug --fresh`.
- `just test [profile]`: build, then `ctest --preset <os>-<profile>` (output on failure; no tests is an error).
- `just run <target> [profile]`: build everything, then run `build/<os>-<profile>/tests/<target>`, e.g. `just run test_events`.
- `just publish [profile]`: build (default `release`) and `cmake --install` into `publish/`.
- `just clean [profile]`: delete `build/<os>-<profile>/`, or `build/` and `publish/` when no profile is given.
- `just docs`: create `build/doxygen` (Doxygen does not create the output path) and run `doxygen Doxyfile`; open `build/doxygen/html/index.html`.
- Without just: `cmake --workflow --preset linux-debug` configures, builds, and tests.

## CI, version tags, and docs

The workflows follow `yizhinailong/mcr` (pinned action SHAs with the version in a comment, checksum-verified tool downloads, logic inline in the YAML); `windows-ci.yml` and `release.yml`, the `workflow_call` trigger and package steps in `linux-ci.yml`, and the Release dispatch in `version-tag.yml` follow mcr's workflows of the same names. `../drogon-openai`'s workflows are copies of these, differing only in the project name and the Test step comments; keep the two repos in step when changing them. `docs/*/ci.md` and `docs/*/doxygen.md` describe the workflows for users; keep those pages in sync.

- `.github/workflows/linux-ci.yml` (Linux CI) runs on every branch push, PR, and manual dispatch, and as a reusable workflow (`workflow_call`) from Release on version tags. Its `push` trigger covers branches only, so a tag runs it only through Release. It runs a `debug` and a `release` matrix leg on `ubuntu-24.04`.
  - Tools: CMake 4.2.3 (Kitware tarball, SHA-256 pinned) and LLVM 21 from apt.llvm.org (signing key fingerprint checked). `/usr/lib/llvm-21/bin` goes on `PATH`, so the presets' plain `clang++` resolves to LLVM 21.
  - Steps: `clang-format --dry-run -Werror` (debug leg only), then `vcpkg install drogon`, then `cmake --preset`, `cmake --build --preset`, and `ctest --preset`.
  - vcpkg is a shallow fetch of the pinned commit `67972e92`, the checkout that provides drogon 1.9.13 port-version 2, the version these docs cite. Bump `VCPKG_COMMIT` (in both CI workflows) only after verifying locally on the same commit.
  - The vcpkg binary cache is restored and saved with `actions/cache/restore` and `actions/cache/save` right after the install, so a failing build still keeps the dependencies. The key includes `ImageOS`, the vcpkg commit, `gcc -dumpfullversion` (vcpkg builds the ports with the system GCC), and the CMake version.
  - On a tag, a step after configure compares the tag with `CMAKE_PROJECT_VERSION` from `CMakeCache.txt`. CMake parses that value itself, which double-checks the tag workflow's text parsing.
  - On a tag, the `release` leg runs `cmake --install` into `$RUNNER_TEMP/drogon-onebot-<version>-linux-x64/`, adds `LICENSE`, packs it as `.tar.gz`, and uploads it as the `drogon-onebot-linux-x64` artifact (7 days).
  - The ubuntu-24.04 image has GCC 12 to 14. Clang 21 uses the newest libstdc++ it finds (14).
- `.github/workflows/windows-ci.yml` (Windows CI) has the same triggers, matrix, tag check, and packaging as Linux CI, on `windows-2025` with `shell: pwsh`. It does not check formatting; the Linux debug leg does.
  - `ilammy/msvc-dev-cmd` sets up the x64 MSVC environment first, which `clang-cl` needs. The CMake 4.2.3 zip and ccache 4.14.2 (the presets hard-wire ccache, and the image has none), both SHA-256 pinned, go on `GITHUB_PATH` after it, so they come before Visual Studio's CMake 3.31. LLVM (`clang-cl`) and Ninja come from the image, which had LLVM 20.1.8 and Ninja 1.13.2 as of image 20261021; the install step prints them.
  - vcpkg uses the same commit, `bootstrap-vcpkg.bat`, and `--triplet`/`--host-triplet` from `VCPKG_TRIPLET` (`x64-windows-static-md`, the same as `just init` and the `windows-base` preset). vcpkg builds the ports with MSVC and its own CMake, so the cache key is `ImageOS`, the triplet, the vcpkg commit, and `VCToolsVersion`.
  - GitHub's pwsh wrapper only checks the last exit code, so `run:` scripts with several native commands set `$PSNativeCommandUseErrorActionPreference = $true`. Don't pipe a native command into `Select-Object -First` there, because stopping it early can count as a failure; index the captured output instead.
  - On a tag, the `release` leg packs `drogon-onebot-<version>-windows-x64.zip` with `Compress-Archive` and uploads it as the `drogon-onebot-windows-x64` artifact.
- `.github/workflows/release.yml` (Release) runs on pushed `v*` tags and on manual dispatch. It calls both CI workflows with `uses:`, then its publish job (tags only, after both pass; the only job with `contents: write`) downloads the `drogon-onebot-*` artifacts and runs `gh release create --verify-tag --generate-notes` with the title `drogon-onebot <VERSION>`, or `gh release upload --clobber` when the release already exists. Runs for one tag queue instead of cancelling each other.
  - The packages hold the release build only, by decision. On Windows that library uses `/MD`, so consumers' Debug builds (`/MDd`) cannot link it (`LNK2038`) and build from source instead.
- `.github/workflows/version-tag.yml` runs on pushes to `master` that touch `CMakeLists.txt`, and on manual dispatch.
  - It reads `VERSION` from the first `project()` call at the push's before and after commits. It strips `#` line comments, and the value must be a literal `major[.minor[.patch[.tweak]]]`. On a change, it creates the annotated tag `v<VERSION>` (`drogon-onebot <VERSION>`) on the pushed commit.
  - A before commit without a usable version is only a baseline. A tag that already points at another commit fails the run; one on the same commit is reused.
  - Tags pushed with `GITHUB_TOKEN` do not trigger push workflows, so it then runs `gh workflow run release.yml --ref <tag>`. That is why Release keeps `workflow_dispatch`.
- `.github/workflows/docs.yml` builds the Doxygen site with Doxygen 1.18.0 (SHA-256 pinned) on pushes to `master` that touch the documented paths, then deploys it to GitHub Pages. Pages must use the "GitHub Actions" source in the repository settings.
  - It appends `WARN_AS_ERROR = FAIL_ON_WARNINGS` through stdin (`( cat Doxyfile; echo ... ) | doxygen -`), so any comment warning fails the run.
  - The `Doxyfile` itself keeps `NO`, because older local Doxygen versions warn about unknown 1.18 tags.
- Check workflow edits with `actionlint` (with `shellcheck` on `PATH`, so the bash `run:` scripts are checked too). actionlint does not check the pwsh scripts of Windows CI; run changed pwsh steps locally with the `GITHUB_*` files pointed at a temp directory.

## Build notes

- Requires CMake >= 4.0, Ninja, and ccache (hard-wired as `CMAKE_CXX_COMPILER_LAUNCHER`). Compiler is `clang++` on Linux, `clang-cl` on Windows.
- The UCRT deprecates `getenv`, and clang-cl warns about every call. Read environment variables with `read_env` in `src/onebot_client.cpp`, which uses `_dupenv_s` on Windows and `getenv` elsewhere.
- Don't set `CMAKE_CXX_STANDARD` here. The library declares `target_compile_features(PUBLIC cxx_std_23)` (the public headers use `std::expected`), which is exported to `find_package` consumers.
- Drogon 1.9.13's `FindFilesystem.cmake` leaves an unset `CMAKE_CXX_STANDARD` defined as `""`, which `target_compile_features` rejects. Both `CMakeLists.txt` and `cmake/drogon-onebot-config.cmake.in` unset the empty value right after finding Drogon. Keep those blocks.
- Sources and public headers are collected with `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)`, so adding a file triggers a re-configure on the next build.

## Code style

New C++ code follows the `cpp-style-ref` skill (CMake + vcpkg variant). Drogon's virtual overrides (`initAndStart`, `shutdown`) keep their upstream names.

Format with `clang-format -i <files>` (root `.clang-format`). Check with `clang-format --dry-run -Werror <files>`. clang-format regroups includes: in `src/actions/*.cpp`, `drogon_onebot/onebot_client.hpp` is not treated as the main header, so it sorts after `details/...`.

`.clang-format` sets `LineEnding: LF`, so the dry run flags every line of a CRLF file. `.gitattributes` (`* text=auto eol=lf`) overrides `core.autocrlf` and checks every file out with LF, Windows included. A working tree from before `.gitattributes` keeps its CRLF files until they are converted or checked out again.
